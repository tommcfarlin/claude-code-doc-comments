# Evaluation

This directory contains the full audit trail for the experiment that tested the doc-comments skill's premise.

## Headline result

The hypothesis — that structured doc comments reduce the input-token cost an agent pays when working in a codebase — was **not supported**. Doc comments increased input tokens to first edit by **14–19%** on the tested fixture/task/model combination.

Read the full writeup in [`report.html`](report.html) (self-contained, no dependencies).

## Experimental design

Three arms, identical code, different doc-comment state:

| Arm | State | Source |
|---|---|---|
| A | All doc comments stripped | `strip-swift-docs.py` run on `origin/main` |
| B | Doc comments generated by this skill | Skill pass run on Arm A's stripped baseline |
| C | Original human-written doc comments | Pristine `origin/main` |

Each arm received 5 fresh, non-interactive `claude -p` sessions running the same locked task prompt against Opus 4.7. 15 runs total. Working tree was reset between runs. Skills, web tools, and clarifying questions were disabled via CLI flags to keep the agent on task.

## The task

> Add a method to WatchlistManager called `markAllEpisodesOfSeasonWatched(mediaId:seasonNumber:episodes:context:)` that marks every episode in a given season as watched. After marking, it should trigger the appropriate notification rescheduling so that any pending notifications for those episodes are cancelled or updated. Follow the existing conventions for ModelContext handling, episode persistence, and notification side effects.

## Reproducing

The scripts contain absolute paths to the original experiment location (`/Users/tommcfarlin/Projects/02-tm/doc-comments-experiment/`). To re-run end-to-end:

1. Clone the fixture: `git clone https://github.com/tommcfarlin/where-can-i-watch-ios.git`
2. Create three worktrees off `origin/main`, one per arm.
3. Run `strip-swift-docs.py --apply` on the Arm A and Arm B worktrees.
4. Run the doc-comments skill on the Arm B worktree.
5. Update the path constants in `run-experiment.sh`, `parse-runs.py`, `build-report.py`.
6. `./run-experiment.sh && python3 parse-runs.py && python3 build-report.py`

The methodology is reproducible on any codebase. The numbers will differ.

## What the data shows

Median input tokens to first edit (lower = better for the hypothesis):

| Arm | Median | Δ vs A |
|---|---|---|
| A — stripped (no docs) | 355,942 | — |
| B — skill-generated | 408,297 | +14.7% |
| C — human-written | 425,455 | +19.5% |

Median discovery tool calls (Read/Grep/Glob/Bash) before first edit were nearly identical across all three arms (5–6). The agent's *strategy* didn't change with docs present — it read roughly the same number of files. But each file in Arms B and C was longer (because of the doc comments), so total input tokens went up.

## Honest caveats

- **N = 5 per arm.** 15 runs total. Variance is real and visible in `report.html`.
- **One fixture, one task, one language, one model.** Results characterize this combination only. They do not generalize.
- **"First edit" is a proxy** for "moment the agent has enough context to act." It does not capture output quality or downstream rework.
- **Opus 4.7 is at the top of the capability scale.** A weaker model might show different deltas. We do not have data on this.
- **The task may be too easy for docs to help.** WatchlistManager's method names are descriptive enough that an agent can find what it needs via grep. A task that required understanding side effects or invariants not visible from signatures might tell a different story.

## What this does not prove

That doc comments are useless. They almost certainly help humans, may help weaker models, and may help on tasks that depend on non-obvious behavior. None of those were tested here.

What this does show: **on this codebase, this task, and this model, the skill's stated premise did not hold.**
