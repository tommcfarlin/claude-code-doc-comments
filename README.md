# Doc Comments

> **Status: hypothesis falsified.** This skill was built on the premise that structured doc comments reduce the input-token cost an agent pays when working in a codebase. A controlled experiment (15 runs across 3 arms on an 11k LOC Swift codebase, Opus 4.7) found the opposite: codebases with doc comments cost the agent **14–19% more** input tokens to first edit, not fewer.
>
> Full report: [`evaluation/report.html`](evaluation/report.html). The skill is preserved as a public artifact but is **not recommended for its original purpose**.

## What this repo is now

A record of a hypothesis, the test, and the result.

This skill was originally pitched as "help your codebase help your agent" — doc comments as compressed contracts that let an LLM understand a function without reading the implementation. The intuition felt right. It turned out to be wrong, at least on the test we ran.

Rather than delete the work or quietly walk it back, this repo keeps everything: the skill code, the original framing, the experiment that contradicted it, the raw data, and the writeup. If you want to test the hypothesis on a different codebase, language, model, or task — the methodology is reusable.

## Original hypothesis (not supported)

A structured doc comment compresses a function's contract — purpose, parameters, return value, side effects, throws — into a few lines. The thinking was: an agent that reads a 6-line doc comment doesn't need to read the 50-line implementation, so docs should reduce total input tokens consumed during the agent's discovery phase.

## What the experiment actually found

Three identical checkouts of the same Swift codebase, varying only in doc-comment state:

| Arm | Doc comment state | Median input tokens to first edit |
|---|---|---|
| A | All doc comments stripped | **355,942** |
| B | Generated by this skill | 408,297 (+14.7%) |
| C | Original human-written | 425,455 (+19.5%) |

The agent read the same number of files in every arm (5–6). Its discovery *strategy* didn't change when docs were present. But each file in Arms B and C was longer because of the doc comments, so total input tokens went **up**, not down.

The mechanism the hypothesis depended on — agents skipping implementations because docs were sufficient — didn't happen. Agents read implementations regardless and now also read the docs on top of them.

Full methodology, per-run tables, charts, and reproduction instructions in [`evaluation/`](evaluation/).

## What this does not prove

That doc comments are useless. They almost certainly help humans. They may help weaker models. They may help on tasks that genuinely depend on understanding side effects or invariants not visible from signatures. None of those were tested here.

What this does show: on a clean, well-named codebase, an Opus-class agent doing a moderate refactor task did not benefit from doc comments. If you were going to install this skill to make your agentic workflows cheaper, the data says: don't.

## If you want to use the skill anyway

It still does what it says — generates structured doc comments for PHP, Swift, JavaScript, and TypeScript. If you value the comments for human readers, or want to test whether the hypothesis holds in *your* codebase, install it:

```bash
git clone https://github.com/tommcfarlin/claude-code-doc-comments.git ~/.claude/skills/doc-comments
```

Then `/doc-comments` is available in any Claude Code session. See [`SKILL.md`](SKILL.md) for behavior and flags.

## Reproducing the experiment on your codebase
